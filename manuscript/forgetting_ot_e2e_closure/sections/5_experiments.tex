\section{Experiments}
\label{sec:experiments}

\subsection{Experimental setup}

We evaluate four named tasks: (1) \textbf{MetroPT-3} industrial sensor streams,
(2) \textbf{ImageNet-32} flow-matching training, (3) \textbf{Packer19}
single-cell trajectory inference, and (4) \textbf{A2D2} LiDAR point-cloud
matching.

\paragraph{Timing levels.}
We report three nested measurement scopes. \textbf{$E_1$ (Sinkhorn time)} ends
at the verified coupling or dual potentials. \textbf{$E_2$ (pipeline time)}
adds the fixed downstream consumer. \textbf{$E_3$ (total time)} covers the
complete model-training, generation, or task-evaluation interval. Speedup is
always baseline time divided by DrainSinkhorn time. If $E_1$ is reconstructed
from an $E_2$ record, the paired consumer time is subtracted within each timing
unit before forming ratios or uncertainty summaries.

\paragraph{Comparisons and controls.}
Fixed-width/dynamic-compaction compares the conventional batch with the full
DrainSinkhorn execution path, including release and physical compaction.
Logical-mask/dynamic-compaction (LM/DC) holds the observed release decisions
fixed and isolates the effect of narrowing the batch. Matched component tests
hold the input, proposal, stopping tolerance, verification schedule,
two-marginal verifier, backend, and downstream consumer fixed. When stopping
controllers reach different residuals, we report achieved residuals and
consumer-output deviations with the timing result.

\paragraph{Workloads and numerical settings.}
The main packed-Triton studies use NVIDIA A100-SXM4-80GB GPUs and cold
initialization. MetroPT-3 uses
$(n,W,\varepsilon)=(16384,16,0.1)$, verification interval 4, and
$\tau=10^{-3}$. Packer19 uses $(16384,8,0.1)$ with the same interval; its
component tests use $\tau=10^{-3}$ and its stopping study sweeps
$10^{-4}$--$10^{-2}$. ImageNet-32 uses PCA500 couplings with
$(1024,8,0.03)$, interval 4, and $\tau=10^{-3}$ for three paired 50,000-update
training runs evaluated at NFE 4, 8, and 16. The A2D2 transfer test uses
PyKeOps at $(n,W)=(8192,8)$ over three real LiDAR clips. Appendix
Table~\ref{tab:workload-configs} gives the endpoint and statistical unit for
each main workload, and Appendix Table~\ref{tab:attribution-map} records the
timing scope and implementation of every attribution contrast.

Section 5.2 measures application runtime across tasks. Section 5.3
measures packed-kernel time as the active batch width changes. Section
5.4 isolates verification, screening, and physical compaction on Packer19.
Section 5.5 changes MetroPT-3 grouping, and Section 5.6 separates numerical
safety from scaling across independent GPU workers.

\subsection{Kernel time by active batch width}

To explain when removed lanes become wall-clock savings, we measure the
width-cost term in \cref{eq:time-difference}. The diagnostic calls the same
packed Triton update at fixed problem size and varies only the width.

\begin{figure*}[!t]
\centering
\includegraphics[width=\textwidth]{figures/MAIN_RESULTS_WIDTH_COST.pdf}
\caption{Packed-update speedup by active batch width.
Each curve reports $g_W(a)=c(W,\xi)/c(a,\xi)$ relative to static width
$W\in\{8,16\}$; all panels use the same axes, and shading propagates the
per-width interquartile endpoints from 30 repeats. Panel titles report
$\Delta=b_mN_{\mathrm{SM}}/n$, which determines scheduling-wave quantization.
The $(n,W,\varepsilon)=(1024,8,0.03)$ setting matches the ImageNet-32 training
solver configuration, which verifies every four updates at tolerance $10^{-3}$;
the plotted metric is packed-update time.}
\label{fig:main-results-width}
\end{figure*}

As shown in \cref{fig:main-results-width}, the measured medians define
$g_W(a)=c(W,\xi)/c(a,\xi)$ for static widths $W=8$ and $16$, using the common
active-width coordinates $a\in\{1,2,3,4,6,8,12,16\}$. For a realized
active width $A_k$, the corresponding summand in
\cref{eq:time-difference} is
$c(W,\xi_k)[1-g_W(A_k)^{-1}]$. The panel value
$\Delta=b_mN_{\mathrm{SM}}/n$ predicts the plateau scale: wave quantization is
coarse at $n=1024$ ($\Delta=6.75$), becomes finer at $n=4096$
($\Delta=1.69$), and is near continuous at $n=16384$ ($\Delta=0.42$).

The diagnostic estimates the packed-update component of
$c_k(a,\xi_k)$. Its $n=1024,W=8$ shape is
consistent with the ImageNet-32 Sinkhorn-time ratio: after the active
width enters the $A\leq6$ region, further lane removal changes the update count more
than packed-update time. The $n=16384$ response provides the corresponding
kernel-time behavior associated with the larger MetroPT-3 gains; the matched
endpoint measures the net effect, including control and
consumer work.

\paragraph{Transfer across backend families.}
The OTT-JAX and PyKeOps rows test the execution principle with independent
implementations. OTT-JAX execution that processes only the remaining problems in each
fixed phase is \COTTNativeActiveSpeedup{} faster than native OTT-JAX on real
ImageNet-32 at $W=16$; its matched fixed-width/dynamic-compaction control assigns
\COTTStaticActiveSpeedup{} to removing completed problems only at phase
boundaries and then rebucketing the remaining problems. On real
A2D2 LiDAR, the PyKeOps compacted path is \CKeopsLiDARActiveSpeedup{} faster than
sequential carry at $W=8$. The ImageNet-32 PyKeOps test gives
\CKeopsImageNetActiveSpeedup{}. The tiled-log implementation reaches $n=65536$
without materializing per-problem cost tensors and supplies the measured capacity
boundary.

\paragraph{Verification and screening.}
As shown in Table~\ref{tab:packer19-components}, batched evaluation of the
two-marginal verifier and the preliminary one-marginal screen reduce OT-stage
time under otherwise matched paths. Each ratio subtracts its paired consumer
time before forming the contrast. To test whether screening delays a release,
we replay all \CPackerShadowNegatives{} screen-negative events with the full
two-marginal verifier. The replay finds \CPackerShadowMissedReady{}
already-releasable lanes; the maximum screen--verifier row-residual difference
is \CPackerScreenDiscrepancy{}.

\paragraph{Physical compaction.}
Logical masking leaves the packed kernel at width eight and has no measurable
effect in the matched control. Dynamic compaction removes 100 of 256 problem
updates and yields \CPackerCompactionOTSpeedup{} OT-stage acceleration with
interval \CPackerCompactionOTRange{}; all 24 paired units favor compaction.
Across the paired-observation medians, endpoint energy falls from 879.9 to
688.1 J, while peak allocated memory rises from 80.8 to 106.9 MiB because of
the compacted buffers. Phase costs are reported separately in
\cref{tab:phase-costs}.

\paragraph{Stopping-tolerance sweep.}
The two-host stopping study repeats the LM/DC comparison at $10^{-4}$,
$3\times10^{-4}$, $10^{-3}$, $3\times10^{-3}$, and $10^{-2}$ without pooling
across tolerances. All arms use the same two-marginal verifier, residual
tolerance, and tight-reference consumer output.

\subsection{MetroPT-3 grouping test}

The grouping test holds a set of 32 real MetroPT-3 problems fixed and changes
only their assignment to windows. Offline every-cycle iteration numbers $q_t$
define the grouping, while verifier-derived iteration numbers $n_t$ measure
executed work. Oracle homogeneous grouping minimizes variation in the required
iteration numbers within each window. Heterogeneous and random groupings
increase the number of updates executed after some problems have completed.
As shown in Table~\ref{tab:metropt-grouping}, the matched
fixed-width/dynamic-compaction ratio grows from
\CMThreeHomogeneousRetirementSpeedup{} to
\CMThreeHeterogeneousRetirementSpeedup{} and 1.235--1.271$\times$ on random
layouts.

\subsection{Numerical safety and scale-out}

\paragraph{Independent finite-precision stress test.}
An independent stress test measures decision behavior on 84 near-threshold
problems and 16 runtime attacks over 1/2/4/8 GPUs. Relative to independent FP64
replay, raw FP32 and TF32 each disagree on three accept decisions; an
outward-bound guard followed by FP64 escalation has zero disagreements in
these 100 cases. This guarded configuration is evaluated separately from the
timed applications.

\paragraph{Timed applications and scaling across GPU workers.}
The timed packed Triton path uses the precision supported by the backend and the
two-marginal verifier. All emitted plans meet both recorded marginal-residual
bounds, and every
endpoint passes its output or quality check. The MetroPT-3 scale-out
study assigns complete windows to independent GPU workers. Four workers achieve
3.965--3.979$\times$ fixed-per-worker throughput scaling on held-out MetroPT
routes, with no Sinkhorn collective between workers; the eight-worker matched
endpoint decomposition appears in \cref{tab:metropt-eight-worker}.
