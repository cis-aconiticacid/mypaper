\section{Experiments}
\label{sec:experiments}

The evaluation asks how much DrainSinkhorn reduces application runtime, which execution components produce the gain, and how completion variation and GPU scheduling determine its operating regime. We first define the tasks and comparisons, then report application results, kernel measurements, component tests, grouping effects, and output checks.

\subsection{Experimental setup}

We evaluate four tasks: MetroPT-3 for industrial sensor streams, ImageNet-32 for flow-matching training, Packer19 for single-cell trajectory inference, and A2D2 for LiDAR point-cloud matching. \Cref{tab:workload-configs} gives the primary configurations. The packed Triton studies use NVIDIA A100-SXM4-80GB GPUs and verify every four Sinkhorn cycles. ImageNet-32 training uses PCA500 feature couplings, three paired seeds, and 50,000 training updates; generation is evaluated at 4, 8, and 16 function evaluations (NFE).

\input{figures/FIG-setup.tex}

We measure $E_1$ (Sinkhorn time) through the verified coupling or dual potentials, $E_2$ (pipeline time) through the downstream consumer, and $E_3$ (total time) through the full training, generation, or task-evaluation interval. Speedup is baseline time divided by DrainSinkhorn time. In the two-host MetroPT-3 and Packer19 component tests, $E_1$ is obtained by subtracting paired consumer time within each observation before computing ratios and uncertainty.

Fixed-width execution keeps the original batch through the final verification. Logical masking (LM) freezes completed states at the original width. Dynamic compaction (DC) removes completed state and narrows the batch. Fixed/DC measures the complete execution change; LM/DC isolates compaction under the same observed release decisions. Component tests fix inputs, initialization, tolerance, verification schedule, verifier, backend, and consumer. Repeats characterize timing variability; training seeds, clips, and host/order/GPU combinations provide the statistical units specified with each result.

\subsection{Application runtime and backend transfer}
\label{sec:application-results}

DrainSinkhorn reduces both solver time and application time, with the size of the benefit depending on the workload. \Cref{tab:main-results} separates the three timing levels. The primary MetroPT-3 pipeline achieves \CMetroCorrectedEndpointSpeedup{} speedup with four independent GPU workers as problem updates fall from \CMetroSlotsStatic{} to \CMetroSlotsActive{}. All three execution orders favor compaction, with an observed range of \CMetroCorrectedEndpointRange{}. The corresponding ratio of fixed to compacted GPU energy is \CMetroCorrectedEnergyFactor{}.

Packer19 shows how solver savings translate to the pipeline. In the same 24 paired observations, LM/DC is $1.540\times$ for Sinkhorn time and $1.2243\times$ through the transition consumer. The shared consumer work reduces the pipeline ratio. ImageNet-32 gains are smaller: across three paired training seeds, the Sinkhorn-time ratio is $1.054\times$ and the full-training ratio is \CFeatureTrainingActiveOverStatic{}. \Cref{tab:imagenet-quality} reports feature-space quality after training, and \cref{tab:imagenet-solver-pairs} gives absolute solver times by seed.

Backend results separate the contribution of compaction from the benefit of a complete execution configuration (\cref{tab:ot-cross-backend}). In OTT-JAX, compaction gives $1.366$--$1.581\times$ over fixed-phase execution at tolerances from $10^{-3}$ to $5\times10^{-3}$. At $10^{-2}$, every problem completes in the first phase and the ratio is $0.995\times$. The native-reference ratio remains $1.732\times$ there because it also includes the change to fixed-phase execution.

On PyKeOps, static batching and logical masking outperform the tested compacted configurations on ImageNet-32. Checking every four updates reaches 16 update rounds, compared with 13 for the static batch, and achieves $1.415\times$ over sequential execution versus $1.549\times$ for static batching. Thus checking frequency and batch removal jointly determine the runtime of these configurations. \subsection{Kernel time by active batch width}
\label{sec:width-results}

The width experiment tests the update-cost term in \cref{eq:time-difference}. It varies active width while holding the packed Triton update and problem size fixed. Each point in \cref{fig:width-cost} summarizes 30 direct primitive calls; the timing covers the two update kernels. Screening, verification, and compaction are measured in the component study.

\begin{figure*}[t]
\centering
\includegraphics[width=\textwidth]{figures/FIG-width.pdf}
\caption{A100 packed-update time versus active batch width on synthetic tensors. Points show medians and whiskers show interquartile ranges from 30 repeats. Each panel uses its own vertical scale in milliseconds. Vertical guides locate initial widths $W=8$ and $W=16$. ImageNet-32 training uses $n=1024,W=8$, with $\varepsilon=0.03$, verification interval 4, and tolerance $10^{-3}$; these training settings provide application context for the primitive measurement.}
\label{fig:width-cost}
\end{figure*}

At $n=1024$, widths one through six have similar update time, followed by a large increase from six to seven. At $n=4096$, the first large increase occurs from one to two; the $n=16384$ curve responds from width one. With row tile size $b_m=64$ and 108 SMs, the one-block-per-SM wave-width estimate $b_mN_{\mathrm{SM}}/n$ is 6.75, 1.69, and 0.42 for these three sizes. The observed steps are consistent with the scheduling-wave explanation.

The small-problem plateau helps interpret the modest ImageNet-32 solver gain: lane removal within the plateau reduces update slots with little change in primitive time. Larger problems have a stronger width response, consistent with the larger MetroPT-3 gains. The application endpoint additionally includes control and consumer work, as expressed in \cref{eq:time-difference}.

\subsection{Packer19 single-variable component tests}
\label{sec:components}

The Packer19 study asks which parts of the execution layer reduce time. It uses one transition workload on two hosts with four A100 GPUs each. Three method orders produce 24 paired observations indexed by host, order, and GPU. Timings are medians after warm-up. As shown in Table~\ref{tab:packer19-components}, each contrast changes one component at tolerance $10^{-3}$.

\input{figures/FIG-components.tex}

Batched verification and the one-marginal screen reduce OT-stage time by factors of $1.133$ and $1.105$, respectively. All 24 paired observations favor each change. Replaying \CPackerShadowNegatives{} screen-negative events with the full verifier finds \CPackerShadowMissedReady{} already-completed problems; the maximum row-residual discrepancy is \CPackerScreenDiscrepancy{}.

Logical masking leaves the packed width at eight and yields a ratio near one. Compaction reduces problem updates from 256 to 156 and gives \CPackerCompactionOTSpeedup{} speedup, with interval \CPackerCompactionOTRange{}. Across paired-observation medians, GPU energy falls from 879.9 to 688.1 J, while peak allocated memory increases from 80.8 to 106.9 MiB. \Cref{tab:phase-costs} gives the separately summarized phase times.

A separate stopping-tolerance sweep tests the same LM/DC comparison over five tolerances. \Cref{fig:stopping-results} shows speedup alongside achieved residual and consumer total-variation distance (TV) from the tight reference. Compaction gives \CPackerCompactionRange{} from $10^{-4}$ through $3\times10^{-3}$. At $10^{-2}$, all eight problems first pass at update 8; the ratio is \CPackerNeutralCompaction{} with 95\% interval \CPackerNeutralCompactionCI{}. This equal-completion case exercises the $R=0$ condition in the model.

\subsection{MetroPT-3 grouping test}
\label{sec:grouping-results}

The grouping test asks whether completion variation within a batch changes compaction benefit. It holds 32 real MetroPT-3 problems fixed and changes their assignment to windows. Offline every-cycle completion iterations $q_t$ define the grouping; verifier-derived iterations $n_t$ measure the executed work. Homogeneous grouping places problems with similar completion iterations together, while heterogeneous and random layouts create more completed lanes inside unfinished batches.

As shown in Table~\ref{tab:metropt-grouping}, the fixed/DC ratio is \CMThreeHomogeneousRetirementSpeedup{} for homogeneous grouping, \CMThreeHeterogeneousRetirementSpeedup{} for heterogeneous grouping, and $1.235$--$1.271\times$ for random layouts. The corresponding dynamic-update fractions are 0.892, 0.802, and 0.764--0.789. These comparisons show how batch assignment changes removable work for the same problem set.

\subsection{Numerical accuracy and application outputs}
\label{sec:numerical-results}

The timed packed Triton applications use the backend precision and the two-marginal verifier. All emitted plans meet the recorded marginal-residual bounds, and all reported consumer and training-quality checks pass. On primary MetroPT-3, maximum row and column residuals are $9.476650\times10^{-4}$ and $1.283915\times10^{-6}$; both execution modes attain failure-window ROC AUC $1.0$. ImageNet-32 quality is evaluated in PCA500 feature space at NFE 4, 8, and 16 (\cref{tab:imagenet-quality}).

\Cref{sec:precision-stress} reports a separate finite-precision stress test of an outward-bound guard and FP64 escalation.
