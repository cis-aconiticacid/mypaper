\section{DrainSinkhorn}
\label{sec:method}

\subsection{Problem: wasted lanes in a fixed-width batch}

Consider a window of $W$ independent EOT problems of the form in
\cref{eq:eot}. A batched backend applies one Sinkhorn cycle to every lane in
parallel. The problems need not pass the stopping rule at the same iteration,
yet conventional fixed-width execution retains all $W$ lanes until the slowest
problem finishes. Earlier completions therefore continue to occupy positions
in later kernels.

DrainSinkhorn targets this cross-problem padding. Its objective is to stop
sending completed problems to later kernels while preserving, for every
problem, the EOT objective, Sinkhorn update, stopping tolerance, two-marginal
release rule, and downstream consumer. It changes which problems receive the
next update; it does not introduce a new OT objective or stopping criterion.

For problem $t$, let $n_t$ be the batched iteration of the first configured
verification at which the problem passes. Before update $k$, the required
survivor width is
\[
A_k=\left|\{t:n_t\geq k\}\right|.
\]
Fixed-width execution always presents width $W$ to the backend. DrainSinkhorn
instead presents width $A_k$, physically removing each problem after its
verified completion.

\subsection{Method: screen, verify, and compact}

DrainSinkhorn repeats four operations. First, it advances every active problem
by one batched Sinkhorn cycle. Second, at the configured verification interval,
it computes a cheap one-marginal screen for all active lanes. Third, it applies
the backend's full two-marginal verifier only to screen-positive lanes. Fourth,
it emits every verified output and compacts all corresponding per-problem
state. The next update then runs on the narrower survivor batch. The
verification interval is the number of batched iterations between consecutive
screen-and-verify rounds.

\subsection{Why the screen preserves the release rule}

Let $F_t$ denote one complete Sinkhorn cycle for problem $t$, including its
marginals, kernel operator, and numerical representation. Standard batching
adds a leading problem dimension but no cross-problem reduction. In ideal
arithmetic,
\begin{equation}
\widetilde F\!\left(\operatorname{pack}(z_1,\ldots,z_W)\right)
=\operatorname{pack}\!\left(F_1(z_1),\ldots,F_W(z_W)\right).
\label{eq:pack-commutes}
\end{equation}
Filtering the problem dimension therefore preserves the update applied to each
survivor.

For one problem, a Sinkhorn cycle is
\begin{equation}
u^{k+1}=a\oslash(Kv^k),\qquad
v^{k+1}=b\oslash(K^\top u^{k+1}),
\label{eq:sinkhorn-cycle}
\end{equation}
where $\oslash$ denotes elementwise division. Immediately after the second
leg, exact arithmetic gives
\begin{equation}
v^{k+1}\odot(K^\top u^{k+1})=b.
\label{eq:updated-marginal}
\end{equation}
The column marginal is current by construction, whereas the row marginal
$u^{k+1}\odot(Kv^{k+1})$ can remain outside tolerance. DrainSinkhorn batches
this row-residual calculation across the active lanes. A problem is
screen-positive when its value
$\widehat r^{\mathrm{row}}_{t,k}\leq\tau_{\mathrm{screen}}$.

Screen-positive status only triggers the full verifier. The implementation
recomputes both marginals and releases a problem only when
\begin{equation}
r_{t,k}=\max\!\left\{
\|\pi_{t,k}\ones-a_t\|_1,
\|\pi_{t,k}^\top\ones-b_t\|_1
\right\}\leq\tau_{\mathrm{stop}}.
\label{eq:release-contract}
\end{equation}
A rejected problem remains active. A false-positive screen adds an unnecessary
verification, while a false-negative screen delays compaction; neither screen
outcome can release a problem by itself. The component tests in
\cref{sec:experiments} replay both cases and evaluate the candidates with the
same two-marginal verifier.

\subsection{Physical compaction and matched controls}

After a problem passes, DrainSinkhorn writes its output and compacts every
per-problem object: source and target descriptors, marginals, dual potentials,
centered shifts, log weights, and scratch buffers. Compaction must preserve the
alignment of these objects so that Equation~\eqref{eq:pack-commutes} continues
to apply to the survivors.

We separate three execution modes. \emph{Fixed-width} execution updates all
$W$ lanes through the common final boundary. \emph{Logical masking} records
per-problem completion and freezes completed states but keeps width $W$.
\emph{Dynamic compaction} removes verified completions and runs subsequent
kernels at width $A_k$. Fixed-width versus dynamic compaction measures the
combined effect of release and width reduction. Logical masking versus dynamic
compaction (LM/DC) holds the observed release decisions fixed and isolates the
effect of physically narrowing the batch.

Equations~\eqref{eq:pack-commutes} and \eqref{eq:updated-marginal} state the
ideal-arithmetic invariants. The experiments separately test fixed-work parity,
achieved residuals, near-threshold decisions, application outputs, and the
timing effects of screening, verification, and compaction.

\subsection{Execution boundary and fallback}

Formal comparisons fix the execution mode, initial width, verification
interval, proposal, tolerance, and fallback policy before timing. Iteration
limits and non-finite states fail closed. The packed Triton implementation may
hand a narrow dynamic-compaction tail to the matched single-problem solver when
the survivor width falls below \texttt{min\_packed\_width}; the formal
MetroPT-3 and Packer19 configurations set this threshold to one.

When one complete problem fits on an accelerator, windows are assigned to
independent complete-device workers. Each device then has an independent update
path and no per-update Sinkhorn collective. Row sharding remains a capacity
path for one oversized problem, but it is not the scale-out path evaluated in
the main experiments.
